§1Summary

A Cheats feature that turns your past Claude prompts into a searchable, reusable prompt library. A Claude Code command reads your session history, analyzes it, and stores curated prompts in SQLite. A new /cheats web page lets you browse, copy, and favorite them.

  • The problem — Good prompts you wrote weeks ago are buried in transcripts. There is no way to find and reuse them.
  • The split — Heavy lifting (read history, analyze, improve) happens in a Claude Code command. The web app only reads. This mirrors the existing /discover feature.
  • The payoff — One page where every reusable prompt you have ever written is curated, improved, tagged, and one click from your clipboard.
Note

The web app never calls an LLM or the network — a hard project rule. All analysis and improvement happens inside the Claude Code command; the page reads pre-computed rows from SQLite.

Takeaway

A Claude Code command writes curated prompts to presets.db; the /cheats page reads them. Browse, copy, favorite.

§2Goals & constraints

In scope

  • Extract user-typed prompts from all projects in ~/.claude/projects/**/*.jsonl.
  • Use Claude to analyze + improve each prompt: dedupe, tag, rate reusability, and store a rewritten version next to the original.
  • A /cheats page: search, filter, sort, copy to clipboard, a detail page per cheat, and favorite (pin).
  • Persist everything in the existing presets.db via a new migration.

Out of scope (YAGNI)

  • Live, in-browser prompt improvement — impossible under the no-LLM-in-web rule.
  • Editing the stored prompt text from the web. Authoring stays in Claude Code.
  • A separate database or package. Reuse what exists.

§3Architecture

Two halves joined only through the database file. The Claude Code side produces; the web side consumes. Neither imports the other.

Why this shape

It is the proven /discover pattern: a Claude Code helper does the expensive, intelligent work and writes a result the web reads cheaply. Here the store is SQLite instead of a JSON manifest, because the data is queried, filtered, and mutated (favorite) — a database fits better than a flat file, and the preset engine already provides the SQLite plumbing.

§4Data model

One new table in the existing database, added through a forward-only migration 002_cheats.sql. The migration runner picks it up automatically on next open; no other schema changes.

The cheats table

ColumnTypePurpose
idINTEGER PKAutoincrement surrogate key.
prompt_hashTEXT UNIQUEHash of the normalized original — the dedupe / upsert key.
originalTEXTThe raw past prompt, verbatim. Not null.
improvedTEXTClaude's rewritten version. Nullable.
intentTEXTShort category / intent label.
tagsTEXTJSON array string of tags.
reuse_scoreINTEGERReusability rating, 0–100.
projectTEXTOrigin project path.
occurrencesINTEGERHow many times this prompt was seen. Default 1.
favoriteINTEGERWeb-writable pin. Default 0.
favorited_atTEXTISO timestamp when pinned. Nullable.
first_seen_at / last_seen_atTEXTISO range across history.
created_at / updated_atTEXTRow bookkeeping, ISO-8601.
Important

The store step upserts on prompt_hash and touches analysis columns only. It must never overwrite favorite or favorited_at — the web owns those. Re-running the command preserves your pins.

Decision: favorite is a column on cheats, not a separate cheat_favorites table. It is strictly one-to-one with a cheat, so a column is simpler than the preset engine's separate pinned_items table (which is many-to-many across presets).

§5Generator pipeline

A skill at .claude/skills/cheats/ holds the logic and scripts; a thin /cheats slash command is the entrypoint. The scripts are standalone Node using better-sqlite3. Claude sits in the middle doing the reasoning the scripts cannot.

  1. Extract — extract.mjs walks ~/.claude/projects/**/*.jsonl (reusing the activity.ts traversal), pulls user-typed prompts, strips tool results, system reminders, command stdout, and hook context, normalizes and hashes them, counts occurrences, and writes .cheats/raw.json.
  2. Analyze — Claude reads raw.json and produces, per prompt: an improved rewrite, an intent label, tags, and a reuse score. It clusters near-duplicates. Output: .cheats/analyzed.json.
  3. Store — store.mjs validates analyzed.json leniently and upserts into the cheats table, preserving favorites. Atomic, partial-success — a bad row is skipped, not fatal.
  4. Refresh — Re-running the command repeats the loop and converges on the current history. Favorites survive; analysis columns update.
Why scripts + Claude

Scripts do deterministic I/O (file walk, hashing, SQLite). Claude does the judgment (improve, tag, rate). This is free — it runs inside your existing Claude Code session — and needs no API key, unlike a script that called the Anthropic API directly.

§6Web layer & UI

Reader & API

A new module packages/presets/src/cheats.ts exposes listCheats(), getCheat(id), and the mutation setFavorite(id, on). Keeping the write in the presets package preserves the rule that packages/core stays pure-read. The web detail page calls getCheat directly in the Server Component, like /commands/[id] does.

RouteMethodDoes
/api/cheatsGETReturns all cheats for the explorer's live refresh.
/api/cheats/[id]/favoritePOSTToggles the favorite flag — the one mutating route.
/cheatsRSCforce-dynamic page; prefetches the list.
/cheats/[id]RSCDetail page; reads one cheat directly.

The page

components/cheats-explorer.tsx mirrors commands-explorer.tsx: a search box, filters by project, tag, and intent, sort by recency / reuse score / occurrences, a favorites-only toggle, and pagination. The detail page shows the original and improved prompts side by side, each with a copy button, plus tags, source project, and the seen-range. A StatCards header summarizes total, favorites, projects covered, and average reuse score.

When the table is empty (fresh clone, command never run), an empty state points the user to run /cheats in Claude Code — the same convention as the /discover empty state.

§7Edge cases & testing

Edge cases

  • Empty database — empty state, no crash. handled
  • Huge history — extract caps at the newest N transcripts, like activity.ts caps at the newest 2000 files. handled
  • Malformed transcript line — skipped, not fatal. handled
  • Bad analysis row — leniently validated before store; dropped if invalid. degrade
  • Re-run clobbers a pin — prevented: upsert never writes favorite columns. must-hold

Testing

No web test suite exists in this repo — npm run build is the type-correctness check. Per-script self-checks cover the logic that can break:

  • extract — normalization, hashing, and dedupe behave (a demo() self-check).
  • store — upsert updates analysis columns and preserves favorite across a re-run.
  • cheats.ts — reader returns typed rows; setFavorite toggles correctly.

§8Approaches & decisions

The open design fork was how analysis reaches the database. Three options were weighed; the rest of the design followed from the four requirement choices already made.

★ Recommended

A · Script extract → Claude analyze → script store

Scripts do I/O, Claude does reasoning. Free, exFAT-safe, matches repo convention.

Not advised

B · One script, no LLM

Pure mechanical extraction. Rejected — cannot "improve" a prompt, which was a requirement.

Not advised

C · Script calls Anthropic API

Rejected — needs an API key and network inside the script. The in-session loop is cleaner and free.
